# はじめに
AIに限らず、自分以外の他者とチームで開発を行う場合は、好き勝手に作業されないよう、規約や規定などのルールが必要になります。

また、ルールを作ったところで無視されることもあります。現場の管理者は、作業者にいかにルールを順守させるかについて頭を悩ませることも多いです。

AIエージェントを用いて開発を行う際、AIエージェントが勝手に極秘データを参照したり、誤ってデータを壊したりしないように制御する必要があります。

正しい道を歩んでもらうために、ガードレールを作り、時には首輪をつけて導いてあげる必要があります。

今回は、AIエージェントにルールを守らせる方法と、人間がAIエージェントの成果物をチェックする方法を紹介します。

# 前提条件

- 本記事では、AIエージェント「GitHub Copilot」を使ったサンプルを紹介します。
- 本記事では、Reactでフロントエンド、Expressでバックエンドを構成するWebアプリケーション開発を対象とします。

# 解説

## AIエージェント開発におけるガードレール
AIエージェントは、放っておくとすぐに暴走します。人間が定めた禁止事項に関しても、ときどき無視します。

最近の事例で、米国のAI企業が、サンドボックス環境下でAIエージェントによるセキュリティテスト中に、閉鎖環境から抜け出して他社にサイバー攻撃を仕掛けたニュースがありました。

簡単に破られないように壁で防御しても、ときどきAIエージェントは穴を見つけて抜け出してきます。

では、最初から防御なんてしても無駄かというと、そうではありません。AIエージェントは、大抵は人間の指示通りに動いてくれます。

ただし、指示する際に「XXX 以外はやってはいけない」と禁止事項を的確に伝える必要があります。

禁止事項を指示しない限りは、好き勝手に動き出す危険性があるため、暴走を防ぐためのガードレールが必要になります。

AIエージェントに与える権限や参照・実行範囲を制限したり、人間による承認を得てからツール実行させたり、API呼び出しを無限に実行させないように回数を制限させたりなど、適切に導いていく必要があります。

## AIエージェントに首輪（ハーネス）をつけた開発
AIエージェントの自走開発を適切に導くための環境を作ることを「ハーネスエンジニアリング」と呼びます。

前述のガードレールもハーネスエンジニアリングのひとつの手法です。

ハーネスエンジニアリングをWebアプリケーション開発に適用する仕組みを紹介します。

### AIエージェントが自分自身を制御する仕組み
AIエージェントに読み込ませるために、ドキュメントをMDファイルで用意します。また、MCPサーバーを使用して外部サービスを利用します。

<details>
<summary>Instructions
</summary>
AIエージェントが常時読み込み、アプリケーションを開発する際の前提となるドキュメントです。

例えば、以下の規約を定義します。

- プロジェクトのディレクトリ構成を定義し、コーディング規約などのファイルの場所、静的解析ツールやメトリクス収集ツールを呼び出すコマンド、開発プロセスの進め方、禁止事項等
- フロントエンドやバックエンドで利用するライブラリ、設計方針
</details>

<details>
<summary>Agents
</summary>
AIエージェントに専門の役割を振る舞わせるためのドキュメントです。

例えば、以下のような役割を定義し、人やAIエージェントが特定のエージェントを指定して作業依頼します。

- Webアプリケーションエンジニアとして、セキュリティやユーザビリティ、パフォーマンスを考慮したアプリケーションを開発するエージェント
- レビューワーとして、設計やソースコードにバグがないか確認するエージェント
</details>

<details>
<summary>Skills
</summary>
AIエージェントが読むための開発手順書です。

開発作業の具体的なステップを定義するドキュメントを事前に用意しておけば、エージェントが勝手に読み取って作業を進めてくれます。

エージェントに対してプロンプトで人間が毎回同じ指示を出す必要はありません。

例）開発フロー用のスキル

開発ブランチを作成→先にテストコードを作成→実機能を作成→セルフレビューを最大５回まで実施→作成内容を人が読むためのレポート作成→PR作成、など

前述したInstructionsとは異なり、常時読み込まれるのではなく、必要な時に必要な部分だけ読み込まれるので、コンテキストの消費を抑えらえます。
</details>

<details>
<summary>MCP
</summary>
AIエージェントが外部ツールやサービスを利用しやすくする仕組みです。

ツールやサービスを提供する事業者がMCPサーバーを共通的なインタフェースで公開し、GitHub CopilotやClaudeなど様々なAIエージェントが同じ方法でアクセスできます。

今回利用するサービスは以下の通りです。

- Context7
    - 最新のライブラリやフレームワークのドキュメント情報をリアルタイムで提供するMCPサーバー
        - AIエージェントは、モデル学習した時点の情報しか理解していないため、開発時点では古くて問題のあるライブラリを使ってしまうことがある。Context7はこれを防ぐ。
- Storybook
    - 社内で用意したStorybookデータやコンポーネント仕様を直接読み込ませるMCPサーバー
        - AIエージェントは放っておくと、フォントや色がバラバラの画面を作りこんでしまうため、統一的なUIデザインを強制させる。
</details>


### 開発環境側でAIエージェントを制御する仕組み

AIエージェントのコンテキストを利用して制御するのではなく、開発環境側でAIエージェントの行動範囲を制限するツールを活用します。

<details>
<summary>Linter/Formatter
</summary>
コードの品質と開発速度を安定させるため、静的解析やコード整形のツールを導入し、AIエージェントに利用させます。

AIエージェントは、プロジェクト全体の整合性や効率性よりも単一のタスク（APIや画面作成など）を解決するためにコードを生成していきます。

例えば、以下に挙げるような問題が発生します。

- 類似する機能が既に存在していても、共通機能として活用するのではなく、個別に同じような機能を量産していく
- 目的ごとに機能やファイルを分割するのではなく、1つのファイルや関数にすべての機能を詰め込んで複雑・膨大になり、修正が難しくなる
- if文やfor文を乱用してコードのネストが深くなり、コードレビューがしづらい

これらの問題を解決するため、今回は以下のツールを導入します。

- Biome
    - コードの整形（インデント、引用符、行の折り返しなど）
    - 認知的複雑度（インデントの深さなど）チェック
    - N+1問題など問題あるSQLチェック（独自ルール）
- oxlint
    - 循環的複雑度（if/switch/while文などの多さ）チェック
    - 引数、関数・ファイルの行数上限チェック
- jscpd
    - 重複コードチェック
- dependency-cruiser
    - レイヤー間の依存関係（routes → controllers → services → repositories → dbの一方通行呼び出しなど）チェック
    - 対象ファイルを読み込んでいるファイル数、読み込まれているファイル数チェック
</details>

<details>
<summary>githooks
</summary>
Gitには、コミットの前後やプッシュの前など、特定のタイミングに決まった処理を仕込めるhooksという仕組みがあります。

例えば、コミット前に以下をチェックして、違反していた場合はコミットをキャンセルさせることができます。

- mainブランチへの直接コミット
- パスワードが書かれた秘密情報ファイルが含まれている
- フォーマットが実行されていないファイルが含まれている

AIエージェント自体にもhooksの仕組みがありますが、時々AIエージェントが実行を忘れる時もあります。確実に実行させるためには、Gitのhooksに仕込むとよいでしょう。
</details>

<details>
<summary>gitleaks
</summary>
ソースコードの中にAWS シークレットキーなどクレデンシャル情報が紛れ込んでいないかをチェックするツールです。

前述のgithooksと組み合わせることで、誤ってGitに秘密情報をコミットするのを防げます。

AIエージェントに「秘密情報をコミットしない」指示を出しても、確実に実行されるわけではないので、仕組みで防ぎます。

Windowsにインストールしていない場合は、Powershellからwingetでインストールしましょう。

```powershell
winget install Gitleaks.Gitleaks
```
</details>

<details>
<summary>Storybook
</summary>
Storybookは、Web開発においてUIコンポーネント（ボタンやフォームなどの部品）をアプリ本体から切り離し、個別に開発・確認・ドキュメント化するためのツールです。

AIエージェントは、放っておくとUIデザインにおいても全体の整合性を考慮せず個別に作成します。ボタンなどの形状や色が画面毎にバラバラになり、統一感のあるデザインになりません。

UIデザインを統一させるため、StorybookでUIデザインのカタログを作成し、AIエージェントに画面作成時に参照させます。

![image.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/4072121/e16ae181-5afc-4d7d-bdd1-d688b0a69c43.png)

AIエージェントからStorybookを参照させるためには、ローカルPC上でStorybookのサービスを起動させるか、またはChromaticのようなSaaSを利用します。

Chromaticは、Storybookの開発チームが運営するクラウド型のUIテストおよびレビュー支援プラットフォームです。ビジュアルリグレッションテスト（画面デザインが意図せず崩れていないか等のテスト）の自動化やチーム間のコラボレーション機能を通じて、フロントエンド開発の品質向上をサポートします。

GitHubアカウントでChromaticにログインしリポジトリを連携すると、GitHub側でそのリポジトリの閲覧・開発権限を持っているメンバーは、自動的にChromaticのプロジェクトにもアクセスできるようになります。

カタログの登録数・更新数の上限はChromaticの料金プランにより異なりますが、MCPでStorybookのカタログを参照させるだけであれば、ChromaticのFreeプランでも事足ります。
</details>

<details>
<summary>テスティングツール
</summary>
AIエージェントが既存機能を壊さないよう、リグレッションテストのためのツールを導入します。

また、コードカバレッジが指定した割合以上になるよう、AIエージェントにテストコードを作成させます。

- ユニットテスト・インテグレーションテストツール
    - Vitest
        - テストランナー
    - coverage-v8
        - コードカバレッジを計測するツール
    - Supertest
        - APIテスト
    - user-event
        - ユーザーの操作をシミュレートするツール
    - jest-dom
        - 画面の状態を検証しやすくする拡張プラグイン
- E2Eテストツール
    - Playwright
        - ヘッドレスモード（ブラウザの画面を非表示にして実行）で、ユーザーがブラウザ上で行う操作を自動化でテストするツール
</details>

## レビュー負荷を軽減する仕組み
### AIエージェントに作らせるPRコメントを工夫する
AIエージェントが量産するソースコードを毎回レビューするのは非常に手間がかかります。とは言え、ノールックでmainブランチにマージしてしまうと、期待通りの機能が出来上がらない可能性があります。

コードは読まないが、何の目的でどのような修正が行われたのかを把握するため、PRのテンプレートを用意して、PRの先頭でAIエージェントにまとめを作ってもらいます。

非エンジニアでもわかりやすい言葉づかいで説明する指示を出さないと、AIエージェントは「コードのXXXにYYYを追加した」といったコードレベルの説明をしてくるので、コードを読まない人には訳が分からない内容になってしまいます。

![image.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/4072121/a2f346bf-31d5-4b3f-9909-a26143801cdc.png)

PRを作成する前のセルフレビュー用のSkillに、PRテンプレートを用意します。

<details>
<summary>PRセルフレビュー用Skillのサンプル
</summary>

```powershell
---
name: pr-self-review
description: PR を作成する前に、ブランチの差分を別エージェント（読み取り専用の pr-reviewer）でレビューし、指摘を直して再レビュー（最大 5 回）したうえで、レポート HTML をユーザーに確認してもらい、承認を得てから PR を作る手順。PR を出す前、push 前にブランチを確認したいとき、自分の変更をレビューしてほしいとき、マージしてよい状態か確かめたいときに必ず使う。Use before creating a pull request, and when asked to self-review changes or check that a branch is ready to merge.
argument-hint: 特に見てほしい観点（任意）
---

# PR を出す前の自己レビュー

`dev-workflow` スキルの 6〜8 段階にあたります。

## 鉄則: レビューは必ず別エージェントで行う

**書いた本人（メインのエージェント）がレビューしても、同じ思い込みをもう一度なぞるだけです。**
「なぜそう書いたか」を覚えている状態では、その前提自体を疑えません。
Lint もテストも通っているのに残るバグがあります（実例は末尾）。

`agent` ツール（サブエージェント）で **`pr-reviewer`** カスタムエージェントを起動し、
**差分とチェックリストだけを渡します**。実装の意図・背景・「ここは大丈夫なはず」は渡しません。
コードが単体で読めるかどうかも含めて見てもらうためです。

> `pr-reviewer` のツールは `read` / `search` だけです。`edit` や `execute` を持つエージェント
> （`webapp-engineer` や既定の Agent）をレビュアーにしないでください。レビュアーに書かせません。

## 手順

### 1. すべてコミットされていることを確認する

git branch --show-current      # feature ブランチであること（main ではない）
git status --short             # 何も表示されないこと

- 未コミットの変更があれば、`dev-workflow` スキルの手順 5（`npm run check` → コミット）に戻ります。レビューした内容と PR に載る内容を一致させるためです
- 挙動を変えたなら、次の docs の更新もコミット済みであること

| 変えたもの | 更新するもの |
| --- | --- |
| 設計 | 手元の設計案（`docs/adr/`）と Issue の決定事項（変えたら再承認を得て、Issue に変更をコメントする） |
| コマンド、レポート | `README.md` |
| MCP の接続設定、エージェントの `tools`、`mcp:check` / `mcp:ping` の検査内容や表示 | `docs/storybook-mcp.md`（見本帳）、`docs/context7-mcp.md`（Context7） |
| セットアップ手順、環境変数 | `docs/setup-windows.md`、`backend/.env.example` |
| API | `backend/openapi.yaml` |
| コーディング規約 | `.github/instructions/` の該当ファイル |
| しきい値 | `.oxlintrc.json`、`biome.json` など |

### 2. コミット前チェックが通ることを確認する

npm run check

- ブランチ確認・自動整形・静的解析・自動テスト・ビルドをまとめて実行します
- **指摘を抑制で逃がしません。** しきい値の引き上げ、`oxlint-disable` / `biome-ignore` の追加、除外設定の追加で通さない
- 自動整形でファイルが変わったら、コミットしてから次に進みます

### 3. レビュー資料を作る

git fetch origin               # 比較元（origin/main）を最新にする
npm run review:diff

`reports/review/` に次の 2 つが作られます（Git 管理外）。

| ファイル | 内容 |
| --- | --- |
| `summary.md` | 比較元、ブランチ、コミット一覧、未コミット・未追跡のファイル、変更の規模、**変更したファイルの結び付き（Ca・Ce・I と比較元からの増減）** |
| `diff.patch` | main から分岐した地点と作業ツリーの差分。未追跡ファイルも含む。`package-lock.json` は除外 |

「未コミットの変更があります」と表示されたら、手順 1 に戻ります。

あわせて、**承認済みの決定事項を `reports/review/decision.md` に貼り付けます**（Git 管理外）。
レビュアーは GitHub を読めないため、ファイルで渡します。

- `gh issue view <Issue番号> --comments` で表示した「決定事項」のコメントと「決定事項の変更」のコメントを、**要約せず、そのまま**貼り付けます（書いた本人が要約すると、本人の思い込みが入るため）
- 複数ある場合は、投稿の古い順に並べます
- ファイルは edit ツールで作ります（PowerShell 5.1 の `>` は UTF-16 で保存するため）
- 決定事項のコメントが無い場合は、設計の承認が済んでいないので、レビューに進まずユーザーに確認します

> 読み取り専用の GitHub MCP サーバーで、レビュアーが Issue を直接読む方法も試しました。
> しかし VS Code で起動できず（2026-09。「開始中」のまま止まり、ログも出なかった）、採用していません。

### 4. レビュー用サブエージェントを起動する

`agent` ツールで **`pr-reviewer`** を指定して起動し、**結果を待ってから**次に進みます。
サブエージェントは追加の質問ができないので、依頼文だけで作業が完結するように書きます。

このリポジトリのブランチ差分をレビューしてください。修正はしないでください。

1. reports/review/summary.md と reports/review/diff.patch を読む
   （無い、または差分が空なら、その旨だけを報告する）
2. diff だけで判断せず、変更されたファイルと、その呼び出し元を開いて確認する
   **summary.md の「変更したファイルの結び付き」に ⚠ が付いたファイルは、呼び出し元を 1 つ残らず開いて確認する**
   （⚠ は、そのファイルを読み込んでいるファイルが多いという印です）
3. reports/review/decision.md（承認済みの決定事項）を読み、実装と食い違っていないか確認する
   （無い、または空なら、その旨を報告する）
4. 次の観点と、一般的なバグを探す
   <手順 5 のチェックリストから、差分に該当するセクションだけを貼る>

報告形式: 指摘ごとに
  - file:line
  - 何が問題か（1 文）
  - どう壊れるか（具体的な入力・操作 → 起きる結果）
  - 確信度（確定 / 疑い）
問題が無ければ「指摘なし」。推測で件数を水増ししないでください。

- **「どう壊れるか」を必ず書かせます。** 再現の筋道を書けない指摘は、たいてい誤検出か好みの話です
- 結果は `reports/review/<ブランチ名>/round-<回数>.md` に保存します（例: `reports/review/feature/12-user-list/round-1.md`）。**レビューの回数は、このファイルの数で数えます**（会話が長くなっても回数を見失わないため）
- 2 回目以降も同じ依頼文で起動し、**前回の指摘は渡しません**（前回の見方に引きずられないため）。直ったかどうかは、手順 6 で自分で確認します

**セキュリティ観点のレビュアーは、毎回必ず別に起動します**（並列。まとめて 1 回と数えます）。
依頼文には次を含めます。

.github/skills/security-review/SKILL.md を読み、表のすべての項目について
「問題あり / 問題なし / 該当なし（理由）」を報告してください。
該当なしを黙って飛ばさないでください。

**`frontend/` に差分があるときは、React の書き方のレビュアーも別に起動します**（同じく並列、まとめて 1 回）。

.github/skills/react-review/SKILL.md を読み、表のすべての項目について
「問題あり / 問題なし / 該当なし（理由）」を報告してください。

差分が大きいときは、さらに観点ごとに分けて並列で起動します。

1. 正しさ（ロジック、境界値、非同期処理、エラー処理）
2. 画面と API の振る舞い（状態の保持、エラー表示、`backend/openapi.yaml` との整合）
3. セキュリティ（**必ず。** `security-review` スキルの確認表）
4. React の書き方（**`frontend/` に差分があれば必ず。** `react-review` スキルの確認表）

### 5. 観点チェックリスト

**差分に該当するセクションだけ**をサブエージェントに渡します。

#### 共通

- [ ] 既存関数のシグネチャ・戻り値の型を変えたなら、**全ての呼び出し元**を確認したか
- [ ] 「影響なし」「使われていない」と書くなら、検索して**実際に確認した**か
- [ ] 無関係な差分が混ざっていないか（`reports/`、`coverage/`、`.env`、書式だけの変更）
- [ ] 検証用の一時ファイルを消したか（`__demo`、`__probe`、サンプルのテストなど）
- [ ] しきい値の引き上げや Lint の抑制コメントを、理由なく足していないか

#### 結び付き（影響の広いファイルを変えたか）

`reports/review/summary.md` の「変更したファイルの結び付き」の表を見て確認します（Issue #31 の決定事項）。

- [ ] **⚠ が付いたファイル**（いま、または比較元で多くから使われている。比較元で多く使われていた削除ファイルにも付きます）は、**呼び出し元を 1 つ残らず**開いて、壊れていないか確かめたか。テストが呼び出し元まで守れているか
- [ ] **使っている数 (Ce) が増えた**ファイルは、増えた依存が本当に必要か。層をまたいでいないか（依存のルールは通っていても、設計として妥当か）
- [ ] **変えやすさ (I) が下がった**ファイルは、役割が変わっていないか。共通部品に業務の知識が入り込んでいないか
- [ ] **「（比較元では対象外）」と出たファイル**（新しく解析の対象に入った）は、置き場所が正しいか

「—」は依存の解析の対象外のファイルです（対象は `backend/src`・`frontend/src` の `.ts`・`.tsx`。`.test.ts`・`.test.tsx` は除く。`.json`・`.css` などは、どこかから読み込まれているときだけ対象）。
「比較元との増減は不明」と出ているときは、比較元を調べられなかったときです（取り出しや解析の失敗）。表の値は、いまの作業ツリーのものとして読みます。**このときは削除したファイルの値が出ず、⚠ も付きません**（凡例にも同じ断りが出ます）。

#### 決定事項（Issue）

- [ ] 承認済みの決定事項と実装が食い違っていないか（決定事項に無い変更、決定事項にある変更の漏れ）
- [ ] 決定事項の「対象外」に書いたことを実装していないか

#### セキュリティ・秘密情報・N+1（自動チェックが見つけられない部分）

**セキュリティの正本は `security-review` スキルです**（IPA 11 項目・OWASP Top 10:2025 をまとめた確認表）。
ここには重ねて書きません。セキュリティ観点のレビュアーには、そのファイルを読ませます。

静的解析は「危険な書き方」しか見つけられないため、次は毎回人が読んで確認します。

- [ ] 一覧の取得で、呼び先の中でループして問い合わせていないか（N+1）
- [ ] レポートの「被疑バグ」に出た**警告**を確認し、直すか、直さない理由を説明できるか
- [ ] `npm audit` の指摘（重大・高はレポートが失敗する）を、更新か理由の説明で片付けたか

#### backend（Express 5 / better-sqlite3）

- [ ] レイヤーの責務を守っているか（routes → controllers → services → repositories）。
      依存の向きは `deps:check` が見るが、**処理をどの層に書いたか**は見ない
- [ ] SQL は `db.prepare()` とバインドパラメータで書き、文字列連結で組み立てていないか
- [ ] better-sqlite3 は同期 API。不要な `await` や、Promise 前提の書き方をしていないか
- [ ] 非同期ハンドラの例外を `try/catch` で握りつぶしていないか（Express 5 はエラーハンドラへ自動で渡す）
- [ ] エラー応答にスタックトレースや SQL を含めていないか（`middleware/errorHandler.ts` を経由しているか）
- [ ] 一覧を返す API で、SQL の回数をテストで確かめたか（`countQueries`）
- [ ] 入力値を controller で検証しているか
- [ ] エンドポイントやレスポンスを変えたなら、`backend/openapi.yaml` も更新したか
- [ ] 環境変数を足したなら、`backend/.env.example` と `docs/setup-windows.md` も更新したか

#### frontend（React 19 / react-router 7 / axios）

- [ ] HTTP 通信は `src/api/` に集約しているか（axios の import は `deps:check` が見る）
- [ ] 通信中・失敗時の表示があるか（エラーを無視していないか）
- [ ] `useEffect` の依存配列に漏れがないか。アンマウント後に state を更新しないか
- [ ] リストの `key` に配列の index を使っていないか
- [ ] 既存の `src/components/` を再利用しているか（同じ見た目の部品を作り直していないか）
- [ ] 入力欄のラベル、画像の `alt`、`button` の `type` があるか
- [ ] 見た目を Tailwind のクラスで書いているか（独自の CSS を足していないか。足した場合は理由を説明できるか）
- [ ] 色や余白に生の値（`#4f46e5`・`w-[37px]`）を直接書いていないか（色・書体と見本帳が名前を付けた寸法は `@theme` の名前、それ以外の寸法は Tailwind の既定のクラス。決まりは `frontend.instructions.md`）
- [ ] 背景に色を敷いた箇所で、文字色も対で使っているか（`bg-brand-600` と `text-fg-onbrand` など。`index.css` に独自の色の名前を足さない）（コントラスト比 4.5:1 以上）
- [ ] `innerHTML` / `dangerouslySetInnerHTML` を使っていないか。トークンを `localStorage` に保存していないか

#### テスト

- [ ] 実装の内部ではなく、**振る舞い**をテストしているか
- [ ] `.only`、意図しない `.skip` / `.todo` を残していないか
- [ ] テストの実行順や、実ファイルの DB に依存していないか（backend は `:memory:` を使う）
- [ ] **同じ振る舞いを二重に確かめていないか。** 入力値だけが違うテストを `it.each` でまとめられないか
- [ ] DB や環境変数を変えるテストが、前後で状態を戻しているか
- [ ] `npm run test:flaky` を実行したか（テストを追加・変更した場合）
- [ ] カバレッジの下限を、テストを足して満たしているか（除外設定を増やして満たしていないか）

#### scripts / 設定（Windows・PowerShell で動くか）

- [ ] npm scripts に POSIX 専用の書き方（`mkdir -p`、`rm -rf`、`$VAR`、シングルクォートでの囲み）を使っていないか。npm は Windows では cmd.exe で実行する
- [ ] `a && b` の連結で、**a が失敗したときにも実行すべき b** が飛ばされないか
- [ ] ツールの出力形式を思い込みで読んでいないか（実際の出力で確認したか）
- [ ] パス区切り（`\` と `/`）の違いで比較や表示が崩れないか

### 6. 指摘を検証して直す（レビューは最大 5 回）

**サブエージェントの指摘は仮説です。裏を取ってから動きます。**
指摘された `file:line` を開き、「どう壊れるか」が本当に起きるか確認します。

| 種類 | 対応 |
| --- | --- |
| 差分の中のバグ | **PR を出す前に直す** |
| 差分と無関係な既存のバグ | 直さない。PR 本文か別の Issue に書く |
| 意図的に対応しない制約 | **PR 本文の「残る制約」に理由付きで書く** |
| 誤検出 | 何もしない。PR 本文にも書かない |

- 「差分の中のバグ」を直したら、`npm run check` → コミット → **手順 3 に戻って次の回のレビュー**を行います
- 「差分の中のバグ」が 0 件になったら、レビューは完了です（誤検出・既存のバグ・意図的な制約だけが残る場合も完了）
- **黙って範囲を狭めません。** 対応しなかったものは必ず書きます

#### 回数の上限

| 状況 | 対応 |
| --- | --- |
| 5 回以内に「差分の中のバグ」が 0 件になった | 手順 7 へ進む |
| 5 回目のレビューでも「差分の中のバグ」が残る | **6 回目は行わない。** 残った指摘をユーザーに報告し、判断を仰ぐ |

5 回を超えるときは、`workflow.instructions.md` の質問の書き方で、たとえば次の選択肢を示します。

- A. 残りを直してから PR を作る（その修正はレビューを通っていないことを PR 本文に書く）
- B. 残りを「残る制約」として PR 本文に書き、別の Issue で対応する
- C. 作業を止めて、設計案から見直す

### 7. レポートを確認してもらい、承認を得る

npm run report
git rev-parse --short HEAD     # 承認をもらうコミット

- 終了コードが 0 で、レポートの「main ブランチとの差分」に未コミットのファイルが無いことを確認します
- **レポートの「変更ファイル」を上から順に全件見ます。** 一時ファイルや生成物が混ざっていないかは、ここでしか気づけません
- **レポートの「被疑バグ」を確認します。** エラーは 0 件であること、警告は 1 件ずつ内容を見て、直すか、直さない理由をユーザーに説明できる状態にします
- `workflow.instructions.md` の質問の書き方で、次を伝えて承認を求めます
  - レポートの場所: `reports/index.html`（ブラウザで開く）
  - 主な数値: テストの件数、Lint の指摘、重複、カバレッジ、ソースの増減
  - セルフレビューの回数と、直したこと
  - **`frontend/` の見た目に差分があるときは、参照した見本帳の部品**（レビュアーには PR 本文が渡らないため、ここで確認する）
  - **Context7 で説明を取り寄せたときは、使ったライブラリの ID と、入っている版で確かめた結果**（同じ理由）
  - コードを読まない人向けの説明（何が変わり、何を確かめたか）
  - 承認をもらうコミットの SHA
- **承認の返答があるまで PR を作りません**
- 承認の後にコミットを追加したら、手順 2 からやり直し、もう一度承認を得ます

### 8. PR を作る

本文を下の書き方で `reports/review/pr.md` に書きます（Git 管理外なので、誤ってコミットしない）。

git push -u origin <ブランチ名>
gh pr create --base main --title "..." --body-file reports/review/pr.md

作った PR の URL をユーザーに伝えます。マージは `pr-merge` スキルで行います。

## PR 本文の書き方

`github-issue` スキルの鉄則（コードを読まない人向けのまとめを必ず付ける）が、そのまま適用されます。

「まとめ」には、`github-issue` スキルの「まとめで使わない言葉」（ファイルパス・関数名・npm スクリプト名・ツール名など）を書きません。
それらは「概要」以降の節に書きます。

## まとめ（コードを読まない方向け）
- 何が変わるか: （利用者やチームから見て、何ができるように・何が防げるようになるか）
- なぜ変えたか: （困っていたこと。今すぐ困っている人がいたか・将来困るおそれだったかを分けて）
- 気を付けること: （作業の手順や使い勝手で変わること。無ければ「なし」）
- 判断してほしいこと: （選択肢と、それぞれを選んだときに起きること。無ければ「なし」）
- トレードオフ: （技術的に最善の案と、日程や使い勝手の都合で選んだ案がずれる場合、その内容。無ければ「なし」）
```

# まとめ
今回は、AIエージェントにルールを守らせ、人間がAIエージェントの成果物を効率よくチェックするための「ハーネスエンジニアリング」の仕組みを紹介しました。

ポイントを振り返ると、以下の3つになります。

- **AIエージェント自身に守らせる仕組み**
    - Instructions、Agents、Skillsで規約や役割、開発手順を定義し、MCPで最新のライブラリ情報やUIデザインのカタログを参照させる
- **開発環境側で強制する仕組み**
    - Linter/Formatter、githooks、gitleaks、Storybook、テスティングツールで、AIエージェントが指示を忘れたり無視したりしても、ルール違反のコードが紛れ込まないようにする
- **人間のレビュー負荷を軽減する仕組み**
    - 非エンジニアでも読めるPRのまとめや、メトリクスのレポートを用意させ、コードを1行ずつ読まなくても変更内容と品質を把握できるようにする

AIエージェントへの指示（プロンプトやドキュメント）だけに頼ると、AIエージェントはときどきルールを破ります。指示で導きつつ、ツールで確実に止め、最後は人間が要点を確認する、という多層の防御にすることが重要です。

これは、人間同士のチーム開発でも同じです。規約を作るだけでなく、守られているかを仕組みでチェックし、レビューしやすい形で成果物を報告してもらうことで、チーム全体の品質が安定します。AIエージェントも、チームの一員として同じように首輪をつけて迎え入れてあげましょう。

一方で、ハーネスを厳しくしすぎると、AIエージェントの自走力を損ない、開発スピードが落ちてしまいます。プロジェクトの規模や重要度に応じて、どこまで制限をかけるかを調整していくことも大切です。

AIエージェントを「放し飼い」にするのではなく、適切なハーネスをつけて、安全かつスピーディーなチーム開発を実現していきましょう。
